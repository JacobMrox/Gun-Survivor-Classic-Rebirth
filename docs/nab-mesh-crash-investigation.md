# Survivor NAB mesh crash investigation

Status: unresolved. No game patch or limit increase has been implemented.

## Loader finding (2026-11-05)

The loader at 0x004118f3 reads an auxiliary array of `vertexCount * 0x3c`
bytes immediately after the variable-sized disk mesh group records, followed at
0x00411915 by `triangleCount * 0x14` bytes. The Tool Hazard Survivor writer
previously preserved both arrays unchanged when changing mesh counts. The
loader therefore consumes later animation data as mesh metadata and ultimately
reads the wrong bone count. A working capture has 14 at model +0x78 and valid
bone chains; the expanded-mesh crash capture has zero there and group pointers
into unrelated memory. This is a concrete serialization defect, not evidence
that the executable imposes a global vertex/triangle limit.

An `ENEM00.mesh-duplicate-aux-test.NAB` diagnostic was generated by duplicating
the original 0x3c-byte vertex and 0x14-byte triangle records alongside the
duplicated geometry. It retains the original animation and texture. It still
requires in-game testing. General generation of these records for new geometry
requires understanding their fields; merely adding zero-filled bytes is not a
proven solution.

## Reproduction

For ENEM00, the user reported that an original-mesh OBJ export/import round trip
(469 triangles) works, while an otherwise original NAB with 98 duplicated
triangles distributed across its visible groups (567 triangles) crashes when the
enemy appears. A 512x512 texture with the original mesh also works. These
observations implicate the changed mesh stream, but do not establish a global
triangle limit: malformed serialization or a slot-specific allocation remain
possible. Other shipped enemy files contain more than 567 triangles.

## Crash evidence

The 2026-11-05 14:33 Windows application event for gun_bio.exe reports
0xc0000005 at module offset 0x196187 (VA 0x00596187 for the observed image).
The corresponding x86 minidump reports a read from 0x48. At the fault, EDX is
0x48 and ESI is 0xfffffffc; the faulting instruction is
`fmul dword ptr [edx + esi*4 + 0x10]`.

The saved return address is 0x0041275f in the native model drawing routine. Its
immediately preceding code obtains a group node pointer from
`[group_table + group_offset + 0x10]`, checks it for zero, then passes
`node + 0x40` as a matrix to the helper. The saved EDI value at the helper entry
is 0x8, so the apparent node pointer is invalid but non-null. Saved EBX is zero,
indicating group offset zero at that point. These facts explain the access
violation; they do not identify what corrupted or incorrectly initialized the
pointer.

The available minidump does not contain the model or group-table heap pages, so
their runtime contents and the loader's allocation cannot be reconstructed from
this dump. Before patching, capture the relevant memory during initialization and
trace the NAB loader, pointer relocation, and any per-instance storage sizing.
Validate a fix with the original model, the duplicated mesh, ported meshes,
several other enemy types, reloads, and multiple simultaneous actors. A guard
that merely skips an invalid pointer would hide the symptom and is not a mesh
limit fix.
